## Physical IMU quaternion interpretation failure and correction

The later physical run is recorded as `IMU-ORIENT-001-R01` in `docs/verification/artifacts/phase2-imu-quaternion-physical-test.log`. The operator reported a Raspberry Pi 4, Ubuntu 22.04.5, ROS 2 Humble, Linux `aarch64`, and a physical Unitree LiDAR connected over UDP with Pi `eth0=192.168.1.2` and LiDAR `192.168.1.62`. The sensor was upright with the cable outlet toward robot rear, making LiDAR `+X` approximately robot-forward and `+Z` approximately robot-up. The model was not reported at that initial run; later closeout evidence identified it as a Unitree L2. The exact firmware remains unconfirmed.

The original direct-mapping binary at commit `543a218` preserved these values as ROS `(x,y,z,w)`, which are retained here as raw SDK arrays:

```text
Position A SDK[0,1,2,3]:
[0.997174387762017, 0.008492527327408243, -0.020583866863103248, 0.0717455350248493]

Position B SDK[0,1,2,3], after approximately 90 degrees clockwise on the floor:
[0.7007950813342897, 0.00004620316598751915, -0.02780864177532758, -0.712820406052987]
```

The direct `SDK [0,1,2,3] -> ROS (x,y,z,w)` interpretation produced an approximately 99.18-degree relative rotation around `[0.9992, 0.0254, -0.0296]`. It therefore **failed** because the physical planar rotation appeared almost entirely around `+X`.

The same values interpreted as `SDK [1,2,3,0] -> ROS (x,y,z,w)` produce Position A roll/pitch/yaw of approximately `(+0.80, -2.42, +8.21)` degrees, Position B of approximately `(+2.28, -2.23, -91.02)` degrees, and an approximately 99.18-degree relative rotation around `[0.0141, -0.0095, -0.9999]`. This matches the observed clockwise planar motion around robot/LiDAR `-Z` and supports the corrected project mapping.

The vendor sources are internally inconsistent. Checked-in SDK2 `example.h` labels `[0,1,2,3]` as `(x,y,z,w)`, the historical/upstream ROS IMU path assigns that direct order, and the historical/upstream dynamic TF uses `[1,2,3,0]`. Physical evidence supports the dynamic-TF reordering. The wrapper now performs that reorder once, retains the finite/norm/normalization checks, and supplies the exact resulting quaternion to both `sensor_msgs/msg/Imu` and `unilidar_imu_initial -> unilidar_imu`. The static validator uses both recorded samples, checks the corrected RPY and predominantly `-Z` relative axis, and retains the direct mapping as a negative control.

At this stage, the correction was supported by recorded hardware data but had not yet been retested in the corrected binary. The later physical retest passed as `IMU-ORIENT-001-R02`. The planar pass still does not verify globally referenced heading, arbitrary 3D accuracy, every downstream interpretation of the dynamic TF parent-child relationship, or either static extrinsic.

During the failed-orientation run, valid clouds were reported as publishing steadily at approximately 11.96 Hz while `Unitree SDK reported a point packet but did not return a point cloud` recurred. That coexistence is not classified as a hardware failure. The focused logging refinement tracks valid-cloud freshness, emits only a throttled debug message for an individual getter miss while valid clouds remain recent, and retains a throttled warning when no valid cloud was published recently. SDK packet parsing and point-cloud conversion are unchanged. Later physical testing passed the repeated cloud/IMU publication structure and observed-rate checks.

This machine configuration is not repository-managed. With it active, clean driver restart passed, physical cable unplug/replug automatically restored publication in the already-running driver, and a Pi reboot restored the profile/address/route without manual network repair. After reboot the launched driver published cloud approximately 11.95–11.97 Hz and IMU approximately 249–250 Hz.

## Statically established behavior

- The launch default is headless; `use_rviz:=true` is explicit.
- YAML topic/frame values are authoritative unless the corresponding launch argument is explicitly non-empty; namespace remains independently configurable and empty by default.
- Default relative outputs remain `/unilidar/cloud` (`PointCloud2`, `unilidar_lidar`) and `/unilidar/imu` (`Imu`, `unilidar_imu`) with best-effort, volatile, keep-last depth 10.
- SDK2 work-mode bits 5–31, 2D mode, transport mismatches, and wait-for-start mode are rejected before SDK initialization. IMU-disabled mode requires `publish_imu_tf=false` and ignores unexpected IMU packets.
- `use_system_timestamp=false` is rejected because no hardware-clock-to-ROS-time conversion exists.
- The canonical IMU conversion maps `SDK [1,2,3,0] -> ROS (x,y,z,w)`, finite-checks and normalizes once, and supplies exactly the same quaternion and timestamp to the IMU message and dynamic `unilidar_imu_initial -> unilidar_imu` transform. The corrected binary passed the recorded planar physical retest; broader arbitrary-3D/global-heading semantics remain unverified.
- A point indication/getter miss is debug-throttled while valid-cloud output remains fresh and warning-throttled when no valid cloud has been published recently; no SDK parsing behavior changed.
- The code-inherited `unilidar_imu -> unilidar_lidar` transform is configurable and sent through `/tf_static`.
- A measured robot-to-IMU static transform is disabled by default, has no numeric defaults, and cannot coexist with the dynamic parent of `imu_frame`.
- Invalid parameters and nonzero initialization results result in a nonzero process status; successful transport is closed during normal destruction.
- Launch/config/RViz resources have install rules and the target verification script checks the installed paths plus `--show-args` without starting the driver.
- SDK selection remains Linux-only and exact for `aarch64` and `x86_64`, with the build-tree selection recorded in `unitree_sdk_library.txt`.
- No `/scan`, navigation, fusion, serial bridge, command, or motor behavior was added.

These bullets remain source-contract claims. Separate Pi evidence verifies the corrected C++ compilation/linking, selected ARM64 archive, installed resources, launch argument parsing, physical Unitree L2 publication, corrected planar mapping, sensor-internal TF publication, restart, Ethernet reconnect, and post-reboot behavior for the tested uncommitted working tree.
