# Evidence Log

## Purpose

This is the durable ledger for evidence actually generated by builds, tests, deployment rehearsals, and hardware trials. The verification plan lives in [`test_matrix.md`](test_matrix.md); planned work does not enter this table as a passing result.

Add an entry whenever a test is performed, including failed, interrupted, and inconclusive tests. Do not omit failures. Use one or more entries when a rerun changes configuration or result.

Evidence rules:

- Reference the exact Git commit and, when applicable, firmware commit/hash and release tag.
- Record the configuration file/revision and any command-line overrides.
- Name the test procedure and exact command(s), not only the subsystem.
- Hardware evidence must identify the robot, Pi/MCU/sensor versions, wiring/configuration, test surface/course, safety setup, and whether wheels were raised or on the floor.
- Link or name durable logs, rosbags, CSV, photos/video, build summaries, or measurement sheets; do not rely on an ephemeral terminal statement.
- Distinguish static analysis, automated software validation, wheels-raised hardware validation, and controlled low-speed floor validation.
- Manuscript claims must trace through an evidence ID to a commit, configuration, procedure, environment, and artifact.
- A documentation requirement or static-analysis finding is not hardware verification.
- Never describe deterministic fusion as a Kalman filter or report deferred SLAM/Nav2 behavior without verified implementation evidence.

No runtime or hardware result is entered by Phase 0. `CODEBASE_DEEP_DIVE.md` remains the principal static-analysis document; its findings retain their original evidence labels and do not constitute completed future fixes.

## Entry guidance

- **Date:** ISO 8601 date/time including timezone when timing matters.
- **Evidence ID:** Stable identifier, preferably derived from the matrix ID plus run number, such as `SCAN-003-R01`.
- **Branch/Commit:** Exact tested branch and full or unambiguous commit hash; never “latest.”
- **Claim or test:** The matrix requirement and specific scenario/boundary.
- **Verification method:** Exact command/procedure and whether automated, static, wheels-raised, or controlled-floor.
- **Artifact:** Repository path, durable storage reference, checksum, or experiment record ID.
- **Result:** Pass, Fail, Blocked, or Inconclusive with the observed value/reason.
- **Environment:** OS/ROS/Pi/MCU/sensor/robot/test configuration relevant to reproduction.
- **Notes:** Deviations, interventions, anomalies, calibration provenance, and follow-up issue/PR.
